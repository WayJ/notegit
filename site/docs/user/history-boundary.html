历史边界：重命名与跨库移动

面向知识库使用者（员工与 Agent）的历史边界说明。依据：架构 §9（「文档标识第一版采用库 ID + 路径；重命名历史依据 Git 跟踪，不承诺跨库永久 ID」）；行为由 S5-T7 场景测试固化（server/test/web-history-rename-boundary.test.ts，2026-10-13）。

重命名：历史可追

在同一个库内重命名（Web 端「重命名」或原生 Git 改名）后：

  • 文档的路径历史页会跟随重命名（Git --follow 语义）：在新路径的历史页可以看到改名前的提交，改名前后连续可追。
  • 旧路径的历史不丢失：旧路径的历史页依然完整（含「改名移走」那一笔提交），随时可回看与还原。
  • Web 重命名以「新路径写入 + 旧路径删除」合为一笔提交、内容逐字节保留，因此 Git 能把它识别为改名（R100），跟随得以生效。
  • 逐提交寻址按该提交当时的实际路径：改名前的提交在「版本预览 / diff」里须用旧路径寻址——用新路径访问改名前的提交会得到 404（该版本处尚无此路径），这不是历史丢失，换旧路径即可解析。

跨库移动：历史不跟随

把文档移动到另一个库 = 在旧库删除 + 在新库新建（两笔独立操作，两个库各自提交）：

  • 旧库历史完整保留：旧库中该路径的历史（含最后一笔删除提交）原样可查，历史版本仍可预览与还原。
  • 新库从新提交起：新库中该文档的历史只包含新库自己的提交——即使两库内容逐字节相同、即使改名跟随已启用，历史也不会跨库拼接。Notegit 不承诺跨库永久 ID（架构 §9），各库历史相互独立。
  • 移动后如在新库再次重命名，跟随同样只回溯到该库自己的第一笔提交。

引用含 commit：旧引用仍可解析

Notegit 的文档引用是三要素：库 + 路径 + commit（与 S5-T6 文档引用规范同一格式）。因此：

  • 指向移动/删除/改名前版本的引用，凭其中的 commit 仍能解析到旧库对应历史版本页——内容不会因移动而失联。
  • 三要素中的路径按该 commit 当时的实际路径理解（见上文「逐提交寻址」）；commit 是解析的锚点。

运维与实现说明（选型记录）
