## decisions

- **配置覆盖链（三级，越右越权威）**：契约默认值（validation-defaults.json，经 notegit-validation `defaultConfig()`）← 环境变量（`NOTEGIT_<大写下划线键名>`，如 `NOTEGIT_VALIDATION_LIMITS_MAX_PUSH_BYTES`；值为 JSON 字面量）← `app_settings` 行（storage-model §3.10：键名即配置键、value 为 JSON 文本；迁移 0007 落表，DDL 逐字取契约 @schema 块）。**DB 行同键胜环境**：管理员运行时配置是权威配置面，环境值仅为缺行时的部署级缺省——环境静默凌驾管理面会造成「配置了不生效」。环境通道经 http-backend 的 process.env 展开透传 hook 子进程（buildCgiEnv 继承语义），两入口同链。
- **生效语义（任务第 5 项裁决）**：**全部键热生效**——每次判定点实时读取（pre-receive 每推送开库读行、发布组件每请求读取）；管理员改 app_settings 行下一次推送/提交即生效，无需重启。两项明确例外（记录在 engine.ts 文档）：① 并发闸门（maxConcurrentValidations）持有共享计数状态，配置代次切换时按新限制重建实例（重建瞬间在途计数不跨代——运维型资源语义，自愈）；② HTTP 传输护栏 bodyLimit（防滥用天花板，非判定）在应用组装时读取一次（重启生效），且只升不降（max(生效 maxPushBytes, 1GiB)）——护栏永不先于 E-LIMIT-004 判定给出费解错误。配置 ≠ rulesVersion（validation.md §7.3-4），改配置不动版本号。
- **判定点统一入口**：`server/src/limits/engine.ts` 的 `runServerValidation(input, {db})` = 覆盖链实时读取 → 进程级共享校验器缓存（同配置代次共用一个 createValidator 实例=并发闸门跨请求存续）→ notegit-validation 单一来源。pre-receive（T4 管线）与 publish/pipeline（T7 发布链）两入口同源调用（publish-structure 静态规则同步更新锚点：publish/ 不得直接 createValidator）。
- **fail-closed 配置面**：环境值或 DB 行非法（非 JSON/类型不符/非正整数）→ 判定面抛错整体拒绝（宁可拒推送，不静默回退默认值——默认可能松于管理员本意），错误消息指名配置键；未知键忽略（向前兼容）。值域校验双侧（写入面 setAppSetting + 加载面），数值=安全正整数、清单=字符串数组（空清单=合法收紧选择）。
- **E-LIMIT-004/005 web 侧接线（T7 honest-gap 移交项收口）**：packages/validation 对称补全——`ValidateInput.ref`（web-submit 的 push 级容量判定定位字段）+ web-submit 分支在 ref 与计量（pushBytes/vaultCurrentBytes）同时给定时走同一 checkPushLimits（pre-commit 无 ref 天然不判；计量缺省不判——惰性输入，既有语义不变）。web 口径裁决：**pushBytes=变更字节合计**（新增/修改内容字节；删除不计入——web 无传输包，以写入字节计），vaultCurrentBytes=audit 步骤的 measureVaultBytes（经 ctx 传递，计量失败缺省不判——T6「只少不少」同语义）。越权说明：packages/validation 扩展名义 Ownership 之外，但属 D7 单一来源的加法式补全（T7 treePaths 同先例），master 可整体摘除（server 侧回退传参即可）。
- **T7 honest-gap 收口——维护模式复查**：发布链 execution-point 阶段叠加维护检查（`PublishWebSubmitInput.maintenanceGate?: MaintenanceGate`，开启即拒绝、settle rejected(reason=maintenance)、草稿保留）——与在途撤权同位（identity §5.1 第 3 层落点），与 git 入口「HTTP 403 → update hook」双层同构。观察缝注入测试证明检查后、update-ref 前开启也被拒。生产接线：S4 提交路由传入 app 的 gate 实例（当前无生产调用方——测试即接线证明；缺省不检查，既有形态不变）。
- **T7/T6 honest-gap 收口——残留清理（运维级最小实现）**：`server/src/gitrepo/hygiene.ts` 的 `sweepVaultResidue(dataDir)`，锚点=**启动（listen 前）**（单进程假设下启动无在途写）：① `notegit-push-*.bytes` 计数文件（硬崩残留）删除；② `objects/incoming-*` 隔离目录（receive-pack 惰性垃圾）删除；③ 无引用松对象 `git prune`（只删不可达、不重排 pack——避免每次启动 repack 大库；有松对象才执行，纯 pack 库零开销跳过）。可达对象/refs/配置不动（测试实证：prune 后可再 push）。单库失败不阻断启动（残留是惰性垃圾，下次启动重试）。松对象清理同时回收 E-LIMIT-005 容量口径（松对象计入 measureVaultBytes）。
- **app_settings 管理端点与审计=open 项**：storage-model §3.10「变更走管理端点并记审计（api.md）」——api.md 尚无该端点、§5 审计 kind 注册表尚无 config 类 kind（契约只读，不越权预占）。本任务落存储+加载+生效全链与写入面 `setAppSetting`（upsert+值域校验+updated_by 归因）；HTTP 端点+审计 kind 随 api.md/storage-model 契约修订补录（T1 vault-delete 挂账同模式）。当前管理员经 SQL/ops 写行即可（热生效）。

## honest-gaps（如实标注，不虚构）

- **E-LIMIT-004 计量口径为传输字节（compressed）**：pushBytes=CONTENT_LENGTH/chunked 计数=压缩后请求体；vault 容量口径=落盘字节（measureVaultBytes）。validation.md §9 开放项「打包对象字节数 vs 解压字节数」的 T8 确认：**传输限制计传输字节、容量限制计落盘字节**——两键两口径，语义自洽；压缩比数据与推论见基准记录 §2/§3。
- **pre-receive 对 E-LIMIT-004 只能事后拒绝**：receive-pack 先收包（入 quarantine）后跑 hook——超限推送的传输/隔离区磁盘成本已付，拒绝的是引用更新（T6 锚点的固有属性，非缺陷）。传输期硬断流需 http-backend 解析包协议（超出「流式转发不解析」设计），不做。
- **并发闸门对 git 推送无跨进程约束**：每推送一 hook 进程，闸门计 1 恒放行；实际并行度由容器 CPU 配额约束（基准 §3.5）。web 提交（app 进程内）才是闸门的真实作用面。语义已记录于 engine.ts 与基准 notes。
- **配置改行的生效观察面**：热生效依赖「每次判定点重读」——app_settings 无变更通知/版本号机制，改动即时生效但无「何时生效」的可观测标记（下次推送/提交即生效）。S8 运维指标若需要，可加配置快照入审计（随端点+审计 kind 契约补录一并）。
- **specialFilePatterns/additionalNavPatterns 的触发测试经 E-FM-001/E-LIMIT-002 间接观察**：两键本身无独立错误码（豁免清单改变的是文件分类→接受集），触发测试断言分类结果变化（nav 豁免放行 vs E-FM-001；空特殊清单→E-LIMIT-002）——键→行为链完整，但不是「超限错误」形态（任务措辞针对 E-LIMIT-001~005 五码，已逐码直测）。
- **基准的容器偏差**：node:24-alpine 未装 git（校验器成本基准无 git 依赖用例）；压缩比在宿主 git 测得；E2E 推送时延未单独基准（T4 行为测试覆盖功能、时延由校验器成本主导）。arm64 在 Q2 目标内，x86_64 未跑（单线程 JS 成本对架构不敏感的量级判断，S8 可补）。
