## decisions

- **步骤链与锚点**：`PUBLISH_STAGES = [candidate, audit, authorization, branch-rules, validation, base-commit, execution-point, update-ref, settle]`。审计 pending 预记录紧跟候选构造、先于一切检查（T6「预记早于校验」同锚点——崩溃覆盖窗口最大化；候选构造 ≈ push 的 pack 接收，先行于 pre-receive）；授权先行内容随后（T5 集成裁决延续）；预期旧 commit 比对按任务文本在内容校验后（草稿有效性不依赖 ref 现值）；execution-point 是 identity §5.1 第 3 层在 web 入口的落点（lifecycle.ts reauthorizeAtExecutionPoint 的 docstring 即预期本任务消费）——update-ref 前实时复查成员/角色/库配置，在途撤权与 main_admin_only 翻转在此拒绝（与 update hook 同构）。
- **预期旧 commit 的双重形态**：显式比对（rev-parse 实际值 vs 预期，不符给 base-commit 阶段的精确冲突拒绝）+ 原子 CAS（`git update-ref <ref> <new> <expectedOld>`，全零旧值=必须不存在）——比对给可读错误，CAS 是并发权威闸门（比对后、执行前的移动仍被拒、绝不覆盖）。CAS 失败归类 base-commit（why=cas-race）。
- **候选提交构造（candidate.ts）**：全 plumbing 全异步——ls-tree 基线 → `hash-object -w --stdin`（字节精确）→ 请求级临时 index（`GIT_INDEX_FILE=os.tmpdir()` 独立文件，请求间互不覆盖——§9「不能全局 checkout」；放系统 tmpdir 而非库目录：E-LIMIT-005 库容量口径不因发布在途虚增）→ `update-index -z --index-info`（bare 库可用的 plumbing 形态，`--cacheinfo` 需工作树）→ write-tree → `commit-tree -F -`（身份/时间戳经 env 注入，服务端归因；committedAt 可注入 → 同输入同 OID 可复现）。**mode 不预过滤**：symlink/gitlink mode 原样进 tree，由共享校验器按 E-PATH-002/003 拒——判定唯一来源在校验器（D7），且与 push 同构（push 的 tree 条目同样到校验器才被拒）。删除不存在的基线路径 = 变更清单与基线不一致，构造期拒绝（push 无此形态——git 客户端产生不出；web 输入需显式防护）。
- **审计链同构**：自有 `preRecordPendingWebSubmit`（vault.web_submit / entry='web' / 主体=认证员工+session 载体 / `detail.pushId` 关联键——与 push 行同键名）；终态**全部消费 T6 导出面**：拒绝 `settlePushRejected`、成功按实际 OID `settlePushByRefState`（两函数本就 web_submit-aware）、中断残留由 `sweepOrphanedPending` 启动清扫标 unresolved（同 push 恢复对账面）。预记录失败 fail-closed（宁可拒发布）。settle 按「行 new_commit vs ref 实际值」核对——update-ref 成功后 ref 又被并发移动 → rejected，不虚报成功。
- **草稿保留语义（draft.ts）**：组件不拥有草稿存储（S4 本体）；任何 `kind:'rejected'`（无论阶段）原样回传提交输入（`preserved:true` + changes/baseCommit/branch，校验阶段附完整报告=错误提示唯一来源）；`kind:'published'` 不带草稿——S4 消费成功态后自删。组件侧不存在删除/覆盖草稿的代码路径（结构保证）。
- **同构性测试（验收场景 S4 核心）方法论**：同一违规样本 = 三类判定路径各一（E-FM-001 frontmatter 缺失 / E-PATH-002 symlink / E-PATH-004 新文件 vs 库内存量路径大小写冲突）。push 侧违规提交以**客户端 plumbing 构造**（read-tree/update-index/commit-tree 后推 OID）——macOS 客户端工作区写不出大小写冲突对（大小写不敏感文件系统折叠路径），plumbing 形态即混合 OS 协作的真实攻击/误用形态。比较口径 runtime 对 runtime：rulesVersion 互等且=运行时 manifest；逐文件错误集全等（码/严重度/消息/行/字段/actual，剥 push 侧 commit 归因）；错误/警告计数互等。合法样本两入口都放行（等价性前提）。
- **packages/validation 扩展（唯一来源内的对称补全）**：`ValidateInput.treePaths`（web-submit/pre-commit 的 E-PATH-004 基线）——pre-receive 侧 T4 已以 `CommitDelta.treePaths` 落地全 tree 基线，web 侧无此输入时同一样本两入口错误集**实际分叉**（isomorphism 先 RED 实证），扩展在共享校验器内补齐（契约 §4「同一提交内」的提交=候选提交，其 tree 含未变更存量路径）；缺省回退变更集内比对，既有语义与 96 项测试不变（knownPaths/treePaths 放宽为 readonly string[]——包内只读）。+5 项包内测试。**越权说明**：Ownership 名义 server/src/publish + server/test，但本扩展是同构性验收（S4 场景）的必要条件且属 D7 单一来源的加法式补全，如 master 另有裁决可整体摘除（server 侧只需回退 pipeline 的 treePaths 传参）。
- **结构性禁跳步（三层）**：①运行器代码断言——每步开始前验证全部前序步骤已执行（违规即抛）；②公共面=publishWebSubmit+PUBLISH_STAGES 两件值导出（无「只更新引用/只构造候选」旁路入口）；③静态规则——`['update-ref', …]` 调用形态在 publish/ 源码恰一次且仅在 pipeline.ts、判定件 import 自唯一来源（ref-rules/notegit-validation）、publish/ 内不得出现错误码字面量（规则不复刻）。
- **hooks.afterStep 观察缝**：每步完成后回调（测试注入在途变更/S4 进度提示）；不改变步骤序列（结构性禁跳步不因观察缝松动）。
- **git-exec.ts 自有 spawn**：与 githttp/git-spawn 同语义（异步强制、超时 SIGKILL、stderr 尾部 reject），加 stdin 字节与 env 注入（hash-object/commit-tree -F -/GIT_INDEX_FILE/身份 env）——githttp 既有导出面按「不动」约束不扩改。

## honest-gaps（如实标注，不虚构）

- **E-LIMIT 计量缺口**：web 提交无 push 请求体 → pushBytes 不计量（E-LIMIT-004 于 web 入口无对应口径，待 T8 裁决是否以变更字节计）；vaultCurrentBytes 已进审计 detail，但**未进校验器输入**——包内 web-submit 分支不判容量（checkPushLimits 仅 pre-receive），传了也是惰性参数，E-LIMIT-005 的 web 侧判定随 T8 配置生效时一并接线。
- **拒绝即松对象**：blob/tree/commit 经 -w 落库后才校验，拒绝时成为无引用松对象（git gc 域；单对象原子写、refs 不动）。与 push 的 quarantine 语义差异：receive-pack 有在途隔离区，web 无批量在途对象——不需要隔离。库容量口径受影响（松对象计入 measureVaultBytes），量级=被拒提交本身，T8 基准时纳入观察。
- **settle 竞态路径**：CAS 成功后 ref 被并发移动 → 行 rejected、结果 kind=rejected（stage=settle）——发布曾生效但按实际结果记拒（不虚报、不自动重试），与 T6 post-receive 同语义；发生窗口极窄（CAS 与核对之间）。
- **提交身份策略留 S4**：identity（name/email）为调用方输入（服务端注入进 commit 对象），员工 username→默认身份的推导策略属 S4 表单/账号域；审计主体恒=认证员工（identity §8），与 commit author 无关（既有 E2E 语义）。
- **维护模式复查**（backup-recovery §3）仍未挂（T5/T6 同一挂账，同一执行点叠加位已在）。
- **结构测试非 RED 先行**：publish-structure 为结构断言（对既有代码的静态/导出面检查），未走 RED（首跑即绿，收紧 update-ref 匹配形态时抓到 PUBLISH_STAGES 阶段字面量的假阳性——证明断言咬合）。行为面（candidate/pipeline/isomorphism/包扩展）全部 RED 先行。
- **pushBytes 计量文件/HTTP 层清扫**等 T6 面未动；web 提交不经 HTTP receive 链，无对应清扫需求（settle 在进程内同步完成；进程中断=行停留 pending → 启动清扫）。
