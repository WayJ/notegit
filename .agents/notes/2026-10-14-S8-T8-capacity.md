## decisions

- **Q7 终值 = 九键维持 + 一键修订建议**（全表与依据见建议稿 G1）：`validation.runtime.maxValidationMemoryMb` **256 → 512（MiB，B2 运维型=MINOR，changelog 记旧值→新值）**。触发依据：实现面是入口查**进程整体 RSS**（packages/validation validate.ts），web-submit 走 app 进程——S7-T8 实测 app 基线 RSS 232MB、本次复跑 240.5MB，距 256 阈值仅 16–24MB；搜索重建/DB 页缓存/Node 升级任一漂移即**全部网页提交 E-RUN-001**。512 = 2× 实测基线，且对 768MB 修正地板（见下）仍是有效保护（app RSS 过半容器即拒新校验合理）。pre-receive hook 进程（独立 RSS 78–160MB）不受影响。rulesVersion 尚为 1.0.0-draft.1（S3 定稿升版未发生），修订建议并入 1.0.0 定稿 changelog（若先定稿则单走 MINOR 1.0.1——两路径均写在建议稿，master 裁决）。
- **512MB 地板复核 → 修正建议 768MB（推荐档 1GB 维持）**：本体 232–240MB + 子进程预算 8 链 × ~17MB（保守值，selection §5）= 136MB + 系统/页缓存/备份瞬态（VACUUM INTO、复制件 fsck 子进程）≥100–150MB ⇒ 512MB 无余量。768MB 留 ~20% 余量。降级路径如实记录：512MB 容器将 `git.maxConcurrentChildren` 调至 4（68MB）可运行但备份窗口紧——不承诺、不推荐。deploy/README 已同步（本任务所有权）；selection.md §5 与 roadmap Q2 行修订属 master（建议稿 G3）。
- **新键 `git.maxConcurrentChildren`（默认 8，运维型）**：服务端每请求 git 子进程并发上限。计数对象 = githttp 每请求 spawn 的 `git http-backend` 链（链内 upload-pack/receive-pack/hook 为其子进程，随链消亡——按链计数即按请求计数）。默认 8 依据：① 每链 ~17MB（selection §5 实测保守值；S7-T8 同量级 8–12MB）× 8 = 136MB 子进程峰值预算 + 本体 232–240MB = 368MB，768MB 地板内自洽；② c=4 并发 sync（8 个 git 请求在途）S7-T8 实测无排队塌陷——8 = 实测无塌陷点 × 2；③ 峰值子进程数 ≈ 2× 并发（S7-T8 §3.2），8 链 ≈ 16–24 个 git 进程上限。
- **超限语义 = FIFO 排队，不拒绝**（选型记录见建议稿 G2）：git 客户端（clone/fetch/push/sync 脚本）对等待透明——排队请求停在 Fastify handler（hijack 之前、body 未消费），TCP 背压天然停住客户端发送，Node server.requestTimeout（默认 300s）兜底；被否备选 = 503 拒绝（在脚本/harness 面产生费解失败，且瞬时高峰即误伤）。实测：gate=2 下 c=4 并发 sync 全部成功、墙钟仅 +3.6%（见 evidence）。
- **与 validation.* 键同链不同册**：覆盖链一致（契约默认 ← `NOTEGIT_GIT_MAX_CONCURRENT_CHILDREN` 环境变量 ← app_settings 行，DB 同键胜环境；fail-closed 非法值指名键拒绝）；注册表独立于 LIMIT_KEY_FIELDS（后者与 validation-defaults.json 双向交叉核对防漂移——本键未入册契约前不进该注册表，交叉核对测试不动）；写入面共用 setAppSetting（S8-T8 起兼收 git 域键）；engine.ts 的未知键告警对 git 域键静默（git-gate 自行读行）。**容量热生效**：每次 acquire 与每次唤醒实时读覆盖链（与 maxConcurrentValidations 的按代次重建不同——单计数器+唤醒现读：上调即刻被等待者利用、下调后超出部分随在途释放自然排干）。
- **接线点 = 认证/授权/维护检查之后、spawn 之前取槽**：401/403/404 与 ensureReceiveSetup 不占槽（闸门只数真实 spawn 的 http-backend 链，receive-setup 幂等且仅首推）。槽位挂子进程 error/close 双路释放（release 幂等）。观察缝 `app.childProcessGate`（active/queued/peakActive 高水位；plain property 而非 decorate——插件封装上下文内的 decorate 对根实例不可达）。命名规避 `.git` 子串（gitrepo-static-rules 静态规则按子串拦 `.git` 磁盘命名形态——`gitChildGate` 会误触，故用 `childProcessGate`，守卫未动）。

## honest-gaps（如实标注，不虚构）

- **闸门只覆盖 githttp http-backend 链**：web 侧（发布管线/搜索/gitrepo 维护）的 runGit 短命令子进程不在此键范围（每请求数量少、ms 级；由 maxConcurrentValidations 间接约束发布入口）——未来需要再扩键，建议稿 G2 记边界。
- **pre-receive hook 是链内孙进程**：不单独计数（随链整体消亡）；hook 内再 spawn 的校验进程开销计入「每链 ~17MB」经验值的误差带——实测每链 8–12MB（库小偏轻），17MB 为保守基线。
- **闸门为进程内单实例语义**：多 app 进程并存只在测试形态出现（生产单实例，架构 §10/process-model §1）；跨进程并发仍由容器 CPU/内存配额约束。
- **默认值无真实企业用量支撑**：Q7 终值依据 = S3-T8 基准（Q2 规格容器）+ S7-T8/S8-T8 合成负载（4 员工×4 库×~1.7MB 世界）——试用方真实负载（库数/文件大小分布/推送频率）落地后如需再校正，走同一条 B1/B2 版本化路径（Q7 建议在试用后保持观察位，建议稿 G1 记录）。
- **app_settings 管理端点与 config.update 审计接线仍未落**（storage-model §5 已注册 config.update kind、api.md 无端点——S3-T8 移交项，非本任务范围）：管理员当前经 SQL/ops 写行（热生效）；建议稿 G5 提请随 api.md 下一批补录（含配置快照入审计）。
