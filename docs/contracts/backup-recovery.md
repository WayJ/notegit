## 0. 范围

本契约固化 Q8：跨存储一致备份边界与快照顺序、维护模式定义、密钥保存方式、全新环境恢复流程与逐项验证清单、升级迁移与回退框架。

不在范围：高可用与多实例（第一版无，架构 §10/§9）；备份频率/RPO/RTO 数值目标（Q9，S8 前与试用企业落实，本契约只提供机制与参数位）；外部对象存储备份（后续评估）。

## 1. 数据分类与备份范围

| 数据 | 权威性 | 是否备份 | 恢复方式 |
|---|---|---|---|
| Git bare 仓库（`/data/git/<vault-id>.git`，每库独立） | 权威：内容、附件、历史、refs | **必须** | 原样恢复目录 |
| 管理数据库：用户、成员权限、凭据哈希、库配置、草稿、审计记录 | 权威 | **必须** | 引擎一致快照回灌 |
| 配置（`/data/config/`） | 权威（部署态） | **必须** | 原样恢复 |
| 密钥（[identity §6.1](identity-credentials.md) 清单：pepper 等） | 权威 | **必须**，但与数据备份分置（§6） | 原样恢复 |
| 派生索引（标题/标签/摘要/搜索索引） | 派生 | 不备份 | 恢复后重建（§7 步骤 8） |
| 容器镜像 / 应用代码 | — | 不入数据备份 | 以版本化镜像标签重现（§9） |
| 日志与指标 | 运维态 | 不入一致备份（可另行按企业要求归档） | 不恢复 |

两侧缺一即失能：只有 Git → 无账号、权限、凭据与审计；只有数据库 → 无知识内容。**不能仅备份 Git**，也不能仅备份数据库【依据：架构 §3.1「管理数据库不是派生索引，不能仅凭 Git 重建；备份必须同时覆盖数据库和 Git 仓库」；Q8 原文要求】。

## 2. 存储布局

Docker 单容器 + 持久数据目录（D6、架构 §10「持久数据目录」）：

```text
/data
├── git/<vault-id>.git   # 每库独立 bare 仓库；路径由数据库稳定 ID 映射（架构 §3.2/§9）
├── db/                  # 若 T1 选内嵌引擎（如 SQLite 文件）；若选外置数据库则数据在其自身容器卷（待 T1）
├── config/              # 应用配置；初始化期含一次性 admin-bootstrap.token（identity §7.1，用后即删）
└── keys/                # token-pepper.key 等，0600（identity §6.1）
```

备份执行者的主机侧访问路径（volume/bind mount 对应目录）随部署规格定稿，待 T1。

## 3. 维护模式（定义）

**定义**：实例级全局写闸门。开启后拒绝一切会改变权威数据的写入；读路径与登录保持可用。这是架构 §10「一致备份需进入维护模式阻止内容与管理数据写入」的入口级展开：

| 写入口 | 维护模式行为 |
|---|---|
| 网页正式提交（发布组件，§5.4 第三入口） | 拒绝：503 + 「维护中」提示，草稿保留不丢失 |
| 网页草稿保存/删除 | 拒绝：503（草稿存数据库，属权威管理数据，§3.1） |
| API 写操作（草稿、提交、上传类） | 拒绝：503，结构化错误含 maintenance 标志（错误协议风格遵 T2 契约；错误码定稿待 T5） |
| Git receive（push） | 拒绝：receive 请求返回 403/明确「维护中」文案；**refs 发现阶段即鉴权的语义不变**（§3.2） |
| 管理操作（成员、角色、库配置、凭据创建/撤销、账号停用） | 拒绝：503 |
| 登录 / 会话创建 | **允许**：会话是临时运行态，不属一致性集合；备份多含陈旧会话无害，丢会话仅需重登 |
| 一切读（网页浏览、API 读、Git clone/fetch） | **允许** |

- **维护期间的写分类**：上表拒绝的是**业务与管理写入**——内容、草稿、权限、凭据、库配置，即 §1 中构成备份一致性集合的权威业务状态。维护模式自身的生命周期事件（开启/关闭、备份完成、恢复对账等运维审计行）与登录会话（D-BR-06）属**运行态写入**：允许发生，但按运行态对待——它们产生于快照之后（§4 步骤 3 起），**不进入备份**；回退到该备份时随快照丢弃，属预期行为而非损失。§5 的引用-审计一致性只约束发布/推送链，不依赖运维审计行。
- 生效机制与延迟：单实例单进程（架构 §9；容器内进程模型待 T1 确认）下闸门为**进程内同步标志**，切换调用返回后对所有后续请求立即生效，**传播上界为 0**。若 T1 落定多进程/多容器形态，闸门必须以共享存储状态为准并定义显式传播上界 T_gate（提案随 T1 一并评审）；此时 §4 步骤 2 的排空检查必须在开启时刻 + T_gate 之后才开始。仅实例管理员可切换，操作记审计（运维事件，见写分类）。
- **范围栅栏**：本节的进程内标志只针对维护模式这一个布尔闸门，**不得援引为任何权限/凭据检查缓存的先例**——认证与授权检查的无缓存约束以 [identity §5.1](identity-credentials.md) 为准。
- 客户端行为：拒绝响应统一可识别，CLI/客户端提示维护中并以线性退避重试**读**操作，不自动重发写请求（细化待 T5/T6）。
- 第一版仅此一档，不设「完全停服」档（§10 未要求，YAGNI）。

## 4. 一致备份流程（快照顺序）

以下步骤可逐项执行与核对：

1. **开启维护模式**（§3），记录开启时间 t0（入 manifest）。
2. **排空在途写**：等待所有已开始的写操作到达终态。排空检查在闸门传播上界经过之后才开始（单进程上界为 0，即开启生效后立即；见 §3）。依据【架构 §4.4「预先记录操作，再在引用更新后核对结果」】：Git receive 在开始时预记录审计行（pending），完成或拒绝后置终态；排空条件 = 权威数据上无 pending 写操作。等待有界超时（默认 300 秒，可配）；超时默认**中止本次备份**并保持维护模式供排查（管理员可显式选择继续，此时该操作按 §5 异常态处理并记录）。
3. **数据库一致快照**：使用所选引擎的一致性机制且不依赖停库——内嵌引擎（SQLite 类）用 `VACUUM INTO`/在线备份 API；PostgreSQL 用 `pg_dump --format=custom`（单快照事务）。引擎与命令待 T1；「单事务一致、不中断服务」为本条硬约束。
4. **Git 仓库快照**：此时无写入，直接文件系统复制 `/data/git/` 全目录（保留权限与属主）；备选 `git bundle --all` 逐库打包作为可移植形态。复制后抽样 `git fsck` 校验。
5. **配置与密钥快照**：复制 `/data/config/`；`/data/keys/` 按 §6 分置为独立密钥件。pepper 处于轮换迁移窗口时，密钥件必须完整包含 retired 条目（[identity §6.2](identity-credentials.md)）。
6. **写备份清单（manifest）**：随备份集存放的 JSON：应用版本、DB schema 版本、DB 引擎及版本、t0 与完成时间、维护模式时长、库数量与**每库默认分支 HEAD OID**、各件字节数、备份工具版本。manifest 是 §7/§8 一切核对的依据。
7. **关闭维护模式**，健康检查通过后记录「备份完成时间」指标与审计事件（§10 运维指标）。
8. **离线验证备份件**：manifest 在、件数齐、抽样哈希核对（校验命令随 T6 gates 固化）。

**顺序依据**：步骤 1–2 之后数据库与 Git 均静止，快照先后不影响一致性；固定「DB → Git → config/keys」仅为流程确定性。被拒备选：不停服热备——两存储分别快照必然横切写窗口，产生「审计有成功记录、ref 未更新」类跨存储不一致【依据：架构 §4.4「审计与 Git 更新不能假设跨存储原子提交」】。

## 5. 一致性要求（备份-恢复双向不变量）

恢复出的实例必须满足：

1. **引用-审计一致**：每个 ref 当前 OID 在 DB 审计/发布记录中有「成功」终态（old→new 相邻成链）；无 pending 残留（排空保证；异常场景备份由 §7 步骤 7 的恢复对账处置，并经 §8 R11 复核）。
2. **无半应用写**：不存在「审计记成功但 ref 未更新」或反向状态【依据：架构 §4.4 恢复核对义务】。
3. **权限-映射完整**：每个仓库目录可经 DB 映射到 vault-id/slug；无孤儿仓库、无孤儿库配置行（§3.2 路径映射在 DB）。
4. **凭据可校验**：pepper 文件版本覆盖全部存量 token_hash 版本（identity §6.2；迁移窗口备份含 retired 条目）。
5. **派生数据不参与判定**：索引一致性以「重建后与 Git 对账」验证，不作为恢复前置（§9 索引延迟可观测）。

## 6. 密钥与配置备份（与数据备份分置）

- 架构 §10 原文：「凭据相关密钥必须另有安全备份。」落地方式：**数据备份件**（DB + Git + config）与**密钥备份件**（`/data/keys/`，外加部署层机密的记录：K3 TLS 私钥位置、K4 DB 口令保管处——见 [identity §6.1](identity-credentials.md)）是两个独立备份件，**分置存储**（不同目录/介质/访问控制），密钥件权限 0600。
- 理由：单件合一则一次泄露 = 数据与机密同时失守；分置后单一失窃不全损。被拒备选：合并单件（管理简单但泄露面最大）。
- 密钥件建议静态加密存放（企业密码保险库 / 加密归档）；载体属企业运维选择，本契约只约束分置、权限与完整性。
- K5 一次性令牌哈希存于 DB，随数据库快照走，不另列。
- 恢复要求两件齐备（§7 步骤 2–3）；缺密钥件时网页可重登改密，但全部 token/会话无法校验，Agent 通道全断——由 §8 清单核对暴露。

## 7. 恢复流程（全新环境）

前置：目标机具备与 manifest 相同版本的镜像（或走 §9 升级路径）、持久卷可写、两件备份齐备。

1. 部署容器（保持维护模式启动）。
2. **恢复配置**：`/data/config/` ← 数据备份件中 config 部分；确认 K4（DB 口令）与 K3（TLS）就位。
3. **恢复密钥件**：`/data/keys/` ← 密钥备份件（含迁移期 retired 条目，如有）。
4. **恢复数据库**：引擎快照回灌（SQLite 恢复文件 / PostgreSQL `pg_restore`；命令待 T1）。
5. **恢复 Git**：`/data/git/` ← 备份复制件，保留权限属主。
6. **版本兼容检查**：manifest 的应用版本与 schema 版本 vs 当前镜像；不同则先完成 §9 升级迁移，再继续。
7. **恢复对账**：启动应用（仍处维护模式）后执行恢复核对——快照中任何处于 pending/待核对 的审计行按架构 §4.4 标为终态（成功/拒绝/处置），并核对全部 refs 当前 OID 与发布/推送记录 old→new 成链（§5 不变量 1–2）。对账任务由应用内置提供（触发形态细化待 T5）。
8. 执行 §8 恢复验证清单，全部通过。
9. **重建派生索引**：应用内触发全量重建，进度与延迟可观测（§9）。
10. 关闭维护模式恢复服务；**记录演练证据**（S8 义务：Q8「S8 演练后记录证据，不能仅备份 Git」；DOD-12 附演练证据）。

## 9. 升级迁移与回退框架

- **版本化**：镜像标签语义化版本；DB 内 `schema_version` 迁移表（版本、顺序，历史行不可改）。迁移**仅前向**、有序、可重入检查，随新版本启动自动执行（迁移工具选型待 T1）。
- **升级流程**：读发布说明兼容矩阵 → 开维护模式 → **升级前一致备份（强制；未完成不得继续）** → 更新镜像 → 启动并自动迁移 → 冒烟检查（健康检查、R1/R6 抽样、一次 push 冒烟）→ 关闭维护模式。
- **回退 = 恢复升级前一致备份**：升级全程处于维护模式、业务数据零写入，备份点即升级前状态，回退**零业务数据损失**——维护期间产生的运维审计行与会话按 §3 写分类随回退丢弃，属预期行为而非损失。**不支持 schema 降级**（新 schema + 旧二进制为未测试组合，明确不支持）。被拒备选：down 迁移脚本（维护成本翻倍且易错）。
- **跨多版本**：按发布说明逐大版本步进（每步完整走一遍升级流程），不允许跳级。
- **Git 数据与迁移解耦**：schema 迁移只操作 DB；Git 仓库格式兼容由随镜像分发的 Git 运行时保证（§10 容器「包含应用、Git 运行环境和数据库」）；不兼容变更必须在发布说明显式声明并附转换步骤。
- **发布前义务**：DOD-13「至少完成一次升级/恢复验证」——S8 演练同时覆盖升级与回退路径并记录证据。

## 10. 待定项、任务关系与决策汇总
