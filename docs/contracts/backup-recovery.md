## 0. 范围

本契约固化 Q8：跨存储一致备份边界与快照顺序、维护模式定义、密钥保存方式、全新环境恢复流程与逐项验证清单、升级迁移与回退框架。

不在范围：高可用与多实例（第一版无，架构 §10/§9）；备份频率/RPO/RTO 数值目标（Q9，S8 前与试用企业落实，本契约只提供机制与参数位）；外部对象存储备份（后续评估）。

## 1. 数据分类与备份范围

| 数据 | 权威性 | 是否备份 | 恢复方式 |
|---|---|---|---|
| Git bare 仓库（`/data/git/<vault-id>.git`，每库独立） | 权威：内容、附件、历史、refs | **必须** | 原样恢复目录 |
| 管理数据库：用户、成员权限、凭据哈希、库配置、草稿、审计记录 | 权威 | **必须** | 引擎一致快照回灌 |
| 配置（`/data/config/`） | 权威（部署态） | **必须** | 原样恢复 |
| 密钥（[identity §6.1](identity-credentials.md) 清单：pepper 等） | 权威 | **必须**，但与数据备份分置（§6） | 原样恢复 |
| 派生索引（标题/标签/摘要/搜索索引） | 派生 | 不备份 | 恢复后重建（§7 步骤 8） |
| 容器镜像 / 应用代码 | — | 不入数据备份 | 以版本化镜像标签重现（§9） |
| 日志与指标 | 运维态 | 不入一致备份（可另行按企业要求归档） | 不恢复 |

两侧缺一即失能：只有 Git → 无账号、权限、凭据与审计；只有数据库 → 无知识内容。**不能仅备份 Git**，也不能仅备份数据库【依据：架构 §3.1「管理数据库不是派生索引，不能仅凭 Git 重建；备份必须同时覆盖数据库和 Git 仓库」；Q8 原文要求】。

## 2. 存储布局

Docker 单容器 + 持久数据目录（D6、架构 §10「持久数据目录」）：

```text
/data
├── git/<vault-id>.git   # 每库独立 bare 仓库；路径由数据库稳定 ID 映射（架构 §3.2/§9）
├── db/                  # 若 T1 选内嵌引擎（如 SQLite 文件）；若选外置数据库则数据在其自身容器卷（待 T1）
├── config/              # 应用配置；初始化期含一次性 admin-bootstrap.token（identity §7.1，用后即删）
└── keys/                # token-pepper.key 等，0600（identity §6.1）
```

备份执行者的主机侧访问路径（volume/bind mount 对应目录）随部署规格定稿，待 T1。

**备份产物布局（落地形态；2026-10-14 ADR D14，B2）**：

```text
<out-root>/<YYYYMMDDTHHMMSSZ>-data/     # 数据备份件（分置件 1）
├── manifest.json                       # §4 步骤 6 全字段（定稿见 §4 manifest 字段表）
├── db/notegit.sqlite                   # 步骤 3：VACUUM INTO（独立文件、无 WAL 伴生）
├── git/<vault-id>.git/…                # 步骤 4：全目录复制（保留权限与 mtime）+ 复制件抽样 fsck
└── config/…                            # 步骤 5：原样复制
<out-root>/<YYYYMMDDTHHMMSSZ>-keys/     # 密钥备份件（分置件 2）
└── keys/token-pepper.key               # §6/identity §6.1 清单；迁移窗口 retired 条目随文件原样入件
```

- 两件恒为**不同顶层目录**（`--keys-out` 可直写另一介质根）；数据件内不得出现 keys、密钥件内不得出现数据域（测试断言）。
- 同 stamp 重跑拒绝覆盖（备份不可静默覆盖）；任一步骤失败删除两件半成品目录并原样上抛——无 manifest 的件不可被误认作完整备份（双保险：离线验证以 manifest-present 为第一核对项）；错误不触碰闸门（保持维护，与排空超时同一保守姿态，管理员显式处置）。

## 3. 维护模式（定义）

**定义**：实例级全局写闸门。开启后拒绝一切会改变权威数据的写入；读路径与登录保持可用。这是架构 §10「一致备份需进入维护模式阻止内容与管理数据写入」的入口级展开：

| 写入口 | 维护模式行为 |
|---|---|
| 网页正式提交（发布组件，§5.4 第三入口） | 拒绝：503 + 「维护中」提示，草稿保留不丢失 |
| 网页草稿保存/删除 | 拒绝：503（草稿存数据库，属权威管理数据，§3.1） |
| API 写操作（草稿、提交、上传类） | 拒绝：503，结构化错误含 maintenance 标志（错误协议风格遵 T2 契约；错误码定稿待 T5） |
| Git receive（push） | 拒绝：receive 请求返回 403/明确「维护中」文案；**refs 发现阶段即鉴权的语义不变**（§3.2） |
| 管理操作（成员、角色、库配置、凭据创建/撤销、账号停用） | 拒绝：503 |
| 登录 / 会话创建 | **允许**：会话是临时运行态，不属一致性集合；备份多含陈旧会话无害，丢会话仅需重登 |
| 一切读（网页浏览、API 读、Git clone/fetch） | **允许** |

- **维护期间的写分类**：上表拒绝的是**业务与管理写入**——内容、草稿、权限、凭据、库配置，即 §1 中构成备份一致性集合的权威业务状态。维护模式自身的生命周期事件（开启/关闭、备份完成、恢复对账等运维审计行）与登录会话（D-BR-06）属**运行态写入**：允许发生，但按运行态对待——它们产生于快照之后（§4 步骤 3 起），**不进入备份**；回退到该备份时随快照丢弃，属预期行为而非损失。§5 的引用-审计一致性只约束发布/推送链，不依赖运维审计行。（2026-10-14 ADR D14 精确化（M4，B5 采纳 (a)「语义不入」）：「不进入备份」= **语义不入**——不参与一致性判定与排空（直接终态、永不 pending，不阻塞排空）；`maintenance.enable` 行写于 §4 步骤 1、早于步骤 3 的 DB 快照，物理上随快照存在，恢复/对账侧将其视为运行态遗留忽略即可（零额外排除机制），manifest 的 t0（maintenance_enabled_at）即为该口径的时序界标；回退到备份时，快照点之后的运维行随快照丢弃，属预期而非损失。）
- 生效机制与延迟：单实例单进程（架构 §9；容器内进程模型待 T1 确认）下闸门为**进程内同步标志**，切换调用返回后对所有后续请求立即生效，**传播上界为 0**。若 T1 落定多进程/多容器形态，闸门必须以共享存储状态为准并定义显式传播上界 T_gate（提案随 T1 一并评审）；此时 §4 步骤 2 的排空检查必须在开启时刻 + T_gate 之后才开始。仅实例管理员可切换，操作记审计（运维事件，见写分类）。
- **范围栅栏**：本节的进程内标志只针对维护模式这一个布尔闸门，**不得援引为任何权限/凭据检查缓存的先例**——认证与授权检查的无缓存约束以 [identity §5.1](identity-credentials.md) 为准。
- 客户端行为：拒绝响应统一可识别，CLI/客户端提示维护中并以线性退避重试**读**操作，不自动重发写请求（细化待 T5/T6）。
- 客户端可见性（2026-10-14 ADR D14，M3 裁决 (b)）：Git receive 的 403 维持 JSON 错误信封（契约一致性优先；标准 git 客户端不渲染 JSON 响应体，push 侧用户看到的是 `The requested URL returned error: 403`）——push 403 即「维护中」的可识别信号（E-MAINT-001），经 `GET /api/v1/admin/maintenance` 复核（api.md §8.4 同注；部署 README 记录同口径）。
- 第一版仅此一档，不设「完全停服」档（§10 未要求，YAGNI）。

## 4. 一致备份流程（快照顺序）

以下步骤可逐项执行与核对：

1. **开启维护模式**（§3），记录开启时间 t0（入 manifest）。
2. **排空在途写**：等待所有已开始的写操作到达终态。排空检查在闸门传播上界经过之后才开始（单进程上界为 0，即开启生效后立即；见 §3）。依据【架构 §4.4「预先记录操作，再在引用更新后核对结果」】：Git receive 在开始时预记录审计行（pending），完成或拒绝后置终态；排空条件 = 权威数据上无 pending 写操作。等待有界超时（默认 300 秒，可配）；超时默认**中止本次备份**并保持维护模式供排查（管理员可显式选择继续，此时该操作按 §5 异常态处理并记录）。（2026-10-14 ADR D14 实现锚点（M2/B5）：排空判据 = storage-model §4 `audit.drain_count` 规范查询——pending|unresolved 在途写计数，**含待核对（unresolved）行**：快照前必须无残留（§5 不变量 1），待核对行只能经恢复对账（§7 步骤 7）清算；首轮判据先行，无在途写立即排空（对应 §3 传播上界 0）。超时中止**不持有闸门**——「超时中止保持维护模式（不半退出）」由结构保证，退出维护只能走显式 DELETE 维护端点；中止无审计行（注册表无对应 kind，增 kind 留裁决），可观测面 = 维护进度端点（api.md §3.3 GET）+ 进程日志。落地形态：备份编排直接调用排空原语 `waitForDrain`（默认 300s 可配 `--drain-timeout-ms`），超时路径不执行关闸；`--force-drain-timeout` 为管理员显式继续通道，manifest.drain 如实记 timeout（§5 异常态由恢复对账处置）。）
3. **数据库一致快照**：使用所选引擎的一致性机制且不依赖停库——内嵌引擎（SQLite 类）用 `VACUUM INTO`/在线备份 API；PostgreSQL 用 `pg_dump --format=custom`（单快照事务）。引擎与命令待 T1；「单事务一致、不中断服务」为本条硬约束。
4. **Git 仓库快照**：此时无写入，直接文件系统复制 `/data/git/` 全目录（保留权限与属主）；备选 `git bundle --all` 逐库打包作为可移植形态。复制后抽样 `git fsck` 校验。
5. **配置与密钥快照**：复制 `/data/config/`；`/data/keys/` 按 §6 分置为独立密钥件。pepper 处于轮换迁移窗口时，密钥件必须完整包含 retired 条目（[identity §6.2](identity-credentials.md)）。
6. **写备份清单（manifest）**：随备份集存放的 JSON：应用版本、DB schema 版本、DB 引擎及版本、t0 与完成时间、维护模式时长、库数量与**每库默认分支 HEAD OID**、各件字节数、备份工具版本。manifest 是 §7/§8 一切核对的依据。
7. **关闭维护模式**，健康检查通过后记录「备份完成时间」指标与审计事件（§10 运维指标）。（2026-10-14 ADR D14（B4）：完成时间以 `backup.completed` 审计行（storage-model §5 既有 kind，直接终态 succeeded、actor_kind=system、运行态写入不入备份一致性集合）为**唯一来源**，呈现于运维指标端点 `backup.last_completed_at`（api.md §3.8，`{wired: true}`）；操作者身份由紧邻的 `maintenance.enable` 行携带，完成行不重复主体。排空超时中止**不写** backup.completed——未完成不记完成时间，可观测面 = CLI 错误输出 + 维护进度端点。）
8. **离线验证备份件**：manifest 在、件数齐、抽样哈希核对（校验命令随 T6 gates 固化）。

**顺序依据**：步骤 1–2 之后数据库与 Git 均静止，快照先后不影响一致性；固定「DB → Git → config/keys」仅为流程确定性。被拒备选：不停服热备——两存储分别快照必然横切写窗口，产生「审计有成功记录、ref 未更新」类跨存储不一致【依据：架构 §4.4「审计与 Git 更新不能假设跨存储原子提交」】。

**manifest 字段定稿（步骤 6；2026-10-14 ADR D14，B3）**：随数据件存放（`<…>-data/manifest.json`），§7/§8 的核对面全部可从本清单核对（形状定义 `server/src/backup/manifest.ts`，必填清单 `REQUIRED_MANIFEST_FIELDS` 供离线验证防漂移）：

| 字段 | 内容 | 契约依据 |
|---|---|---|
| backup_id | UTC 秒级时间戳（件目录名基） | §4 步骤 6（随备份集存放） |
| app_version / backup_tool_version | server 包版本 / 备份工具版本常量 | §4 步骤 6「应用版本」「备份工具版本」 |
| host | 主机标识（os.hostname，可注入） | 任务补记「主机标识」 |
| db.engine / engine_version / schema_version | sqlite / sqlite_version() / max(schema_version) | §4 步骤 6「DB 引擎及版本」「DB schema 版本」（D-BR-03 双版本） |
| time.maintenance_enabled_at / completed_at / maintenance_duration_ms | t0 / 完成时刻 / 维护时长 | §4 步骤 1/6/7 |
| vault_count / vaults[]（id、slug、default_branch、head_oid） | 每库默认分支 HEAD OID；空库 unborn → null | §4 步骤 6、D-BR-03 |
| items.data（dir_name、bytes、domains{git,db,config}、files[]） | 件名 / 内容字节合计（不含 manifest 自身）/ 域字节 / 文件级 SHA-256 清单 | §4 步骤 6「各件字节数」；步骤 8 哈希核对的材料 |
| items.keys（dir_name、bytes、files[]） | 同上（密钥件） | §6 |
| drain（outcome、waited_ms） | 排空实况；timeout 仅出现于管理员显式继续的异常态 | §4 步骤 2、§5 |
| fsck（mode、sample_size、checked[]、failures） | 抽样实况；failures 非空不会出现在成功产物（fsck 非零一律中止） | §4 步骤 4「复制后抽样 git fsck」 |

**「各件字节数」口径**：件**内容**字节合计——manifest.json 自身不计入（自含哈希/字节不可构造）；文件级清单（sha256+bytes）覆盖两件全部内容文件且不含 manifest.json。离线验证复算全量（比步骤 8 的「抽样哈希核对」更强，离线核对频率低、不吝全量）。

## 5. 一致性要求（备份-恢复双向不变量）

恢复出的实例必须满足：

1. **引用-审计一致**：每个 ref 当前 OID 在 DB 审计/发布记录中有「成功」终态（old→new 相邻成链）；无 pending 残留（排空保证；异常场景备份由 §7 步骤 7 的恢复对账处置，并经 §8 R11 复核）。
2. **无半应用写**：不存在「审计记成功但 ref 未更新」或反向状态【依据：架构 §4.4 恢复核对义务】。
3. **权限-映射完整**：每个仓库目录可经 DB 映射到 vault-id/slug；无孤儿仓库、无孤儿库配置行（§3.2 路径映射在 DB）。
4. **凭据可校验**：pepper 文件版本覆盖全部存量 token_hash 版本（identity §6.2；迁移窗口备份含 retired 条目）。
5. **派生数据不参与判定**：索引一致性以「重建后与 Git 对账」验证，不作为恢复前置（§9 索引延迟可观测）。

## 6. 密钥与配置备份（与数据备份分置）

- 架构 §10 原文：「凭据相关密钥必须另有安全备份。」落地方式：**数据备份件**（DB + Git + config）与**密钥备份件**（`/data/keys/`，外加部署层机密的记录：K3 TLS 私钥位置、K4 DB 口令保管处——见 [identity §6.1](identity-credentials.md)）是两个独立备份件，**分置存储**（不同目录/介质/访问控制），密钥件权限 0600。
- 理由：单件合一则一次泄露 = 数据与机密同时失守；分置后单一失窃不全损。被拒备选：合并单件（管理简单但泄露面最大）。
- 密钥件建议静态加密存放（企业密码保险库 / 加密归档）；载体属企业运维选择，本契约只约束分置、权限与完整性。
- K5 一次性令牌哈希存于 DB，随数据库快照走，不另列。
- 恢复要求两件齐备（§7 步骤 2–3）；缺密钥件时网页可重登改密，但全部 token/会话无法校验，Agent 通道全断——由 §8 清单核对暴露。
- 权限口径（D-BR-04「密钥件权限 0600」的落地解释；2026-10-14 ADR D14，B2）：目录需要 x 位才可遍历，故**文件 0600、件根与 keys 目录 0700**，复制后 chmod 强制（不信任 umask/来源权限），离线验证与演练按此断言。
- K3/K4 记录义务（2026-10-14 ADR D14，B6）：密钥备份件按 identity §6.1 清单覆盖 **K1**（`/data/keys/` 全目录，含 retired 条目）；**K3（TLS 私钥）/K4（DB 口令）** 的「记录」（保管位置，非机密本体）属部署层——工具不代管、不虚构：K3/K4 保管处记录须与密钥件同置保存（本节首条「外加部署层机密的记录」的落地；deploy/README「备份」节记录该运维义务）。K5 一次性令牌哈希在 DB 内随快照走（本节原文）；K2 盐内嵌口令哈希串同库。备份频率/RPO/RTO 数值（Q9）不预设——机制与参数位已备（`--drain-timeout-ms`、外部触发形态），数值留试用方落实。
- 恢复侧义务（2026-10-14 ADR D14，RS6）：恢复流程不代管 K3/K4 的搬运与就位核验（K4——SQLite 单文件形态现无此项）；`config-restored` 核对项以注记呈现该运维义务（记录随密钥件同置保管，同上）；K5（一次性令牌哈希）随 DB 快照走。

## 7. 恢复流程（全新环境）

前置：目标机具备与 manifest 相同版本的镜像（或走 §9 升级路径）、持久卷可写、两件备份齐备。（2026-10-14 ADR D14（RS4）：**恢复前核验** = 复用 §4 步骤 8 离线验证全量——manifest 在、件数齐、逐文件哈希、HEAD/库行互证、快照库完整性；篡改产物在装载前被拒且**目标不被触碰**，不另立恢复侧校验命令。**目标全新前置**：目标四域（db/git/config/keys）任一非空即拒——恢复不得覆盖既有实例（覆盖 = 半恢复混合态，无核对语义）；镜像 `/data` 预建四空域视为全新。装载后完整性：两件清单逐文件在**目标**复算哈希 + 每库 HEAD == manifest + 目标库 integrity/库行互证——装载环节自身的损坏可检。）

1. 部署容器（保持维护模式启动）。（2026-10-14 ADR D14（RS2）：落地形态 = `NOTEGIT_MAINTENANCE_ON_START=1` 环境变量设闸门**初态**（部署编排参数，恢复/升级场景由部署侧设置；缺省不设/非 '1' 与普通部署行为完全一致）。生命周期端点语义不变（POST/DELETE 仍可切换；POST 对已开闸门幂等无迁移、不记审计行——恢复启动的「开闸」属 §3 运行态生命周期事件「允许发生」非必须）；进度面如实呈现 enabled=true，恢复收尾相位以此复核「确实以维护态启动」（fail-closed：非维护态执行恢复核对 = 本节违序，拒绝）。）
2. **恢复配置**：`/data/config/` ← 数据备份件中 config 部分；确认 K4（DB 口令）与 K3（TLS）就位。
3. **恢复密钥件**：`/data/keys/` ← 密钥备份件（含迁移期 retired 条目，如有）。
4. **恢复数据库**：引擎快照回灌（SQLite 恢复文件 / PostgreSQL `pg_restore`；命令待 T1）。
5. **恢复 Git**：`/data/git/` ← 备份复制件，保留权限属主。
6. **版本兼容检查**：manifest 的应用版本与 schema 版本 vs 当前镜像；不同则先完成 §9 升级迁移，再继续。（2026-10-14 ADR D14（RS4）：本核对前移到装载前执行——schema 版本**高于**当前镜像必拒（D-BR-05 不支持降级）；等于（同版）或低于（启动自动前向迁移，§9）放行；app 版本差异放行并注记（数据面恢复不因 app 版本阻断——升级/兼容矩阵属 §9）。）
7. **恢复对账**：启动应用（仍处维护模式）后执行恢复核对——快照中任何处于 pending/待核对 的审计行按架构 §4.4 标为终态（成功/拒绝/处置），并核对全部 refs 当前 OID 与发布/推送记录 old→new 成链（§5 不变量 1–2）。（2026-10-14 ADR D14（RS3）触发形态定稿，原文「细化待 T5」在此收口：**只读核对**（`restoreReconcile`）与**处置任务**分工——只读核对覆盖残留面（pending/unresolved 发布行为零——排空保证的恢复侧复核）+ 成链面（逐库逐 ref：成功事件 old→new 有序相邻、链尾 == ref 当前 OID、ref 无成功记录/审计有记录但 ref 不存在均点名——§5 不变量 1–2 与半应用写两向），异常态**报告并拒绝放行**；处置任务按「行 new_commit vs ref 实际 OID」标终态（相等→succeeded/不等→rejected，架构 §4.4）+ 孤儿检查 + 对账结果报告，由对账域 CLI 在维护内执行。衔接缝：异常态备份（drain timeout 强制继续，manifest.drain.outcome=timeout）恢复时，先由处置任务清残留，再跑恢复收尾（其错误信息明示这一顺序）。R11 的「管理页抽查」现以库内独立抽查（只读 SQL：无残留、全部 succeeded、主体=认证员工）+ 收尾输出为证据面，审计读取端点是否补待裁决。）
8. 执行 §8 恢复验证清单，全部通过。
9. **重建派生索引**：应用内触发全量重建，进度与延迟可观测（§9）。
10. 关闭维护模式恢复服务；**记录演练证据**（S8 义务：Q8「S8 演练后记录证据，不能仅备份 Git」；DOD-12 附演练证据）。

**恢复运行形态（落地手册；2026-10-14 ADR D14，RS1）**：两相位 CLI——`restore`（离线相位）+ `finalize`（实例侧相位），不做一次性长命令、不做管理端点。十步映射：

| 步骤 | 落地面 |
|---|---|
| 1 部署容器（保持维护模式启动） | `NOTEGIT_MAINTENANCE_ON_START=1` 启动应用（RS2） |
| 2–5 恢复 config/keys/db/git | `restore` 离线装载（应用未启动——SQLite 文件回灌必须避开运行实例的句柄） |
| 6 版本兼容检查 | `restore` 内置（装载前：schema 高于当前必拒 D-BR-05；app 版本差异放行并注记走 §9） |
| 7 恢复对账 | `finalize`（维护内；RS3 分工） |
| 8 §8 清单 | 外部核对（演练脚本断言化 R1–R14；CLI 不代跑浏览器/Git 客户端核对） |
| 9 重建派生索引 | `finalize` 经实例端点触发全量重建（闸门 allowlist 已裁，维护内放行） |
| 10 关闭维护 | **外部显式操作**（DELETE 维护端点）——结构性不在 finalize 内：步骤 10 的前置是「§8 全部通过」，只有外部核对者知道清单结果 |

依据：离线/在线两相位的边界是**诚实性**边界——文件回灌必须无实例参与（运行中的应用持有 SQLite 句柄且启动即迁移/清扫，装载必须先于首启）；而对账/重建/退出维护必须**在维护内**且经实例自身机制（闸门进程内语义，B1 同因）。被拒备选：单命令全流程（要么在命令内起停应用——CLI 越权承担进程编排，要么混合两态——句柄冲突）；管理端点恢复（产物传输与大目录复制不宜绑长请求，B1 同因）。

## 9. 升级迁移与回退框架

- **版本化**：镜像标签语义化版本；DB 内 `schema_version` 迁移表（版本、顺序，历史行不可改）。迁移**仅前向**、有序、可重入检查，随新版本启动自动执行（迁移工具选型待 T1）。
- **升级流程**：读发布说明兼容矩阵 → 开维护模式 → **升级前一致备份（强制；未完成不得继续）** → 更新镜像 → 启动并自动迁移 → 冒烟检查（健康检查、R1/R6 抽样、一次 push 冒烟）→ 关闭维护模式。
- **回退 = 恢复升级前一致备份**：升级全程处于维护模式、业务数据零写入，备份点即升级前状态，回退**零业务数据损失**——维护期间产生的运维审计行与会话按 §3 写分类随回退丢弃，属预期行为而非损失。**不支持 schema 降级**（新 schema + 旧二进制为未测试组合，明确不支持）。被拒备选：down 迁移脚本（维护成本翻倍且易错）。
- **跨多版本**：按发布说明逐大版本步进（每步完整走一遍升级流程），不允许跳级。
- **Git 数据与迁移解耦**：schema 迁移只操作 DB；Git 仓库格式兼容由随镜像分发的 Git 运行时保证（§10 容器「包含应用、Git 运行环境和数据库」）；不兼容变更必须在发布说明显式声明并附转换步骤。
- **发布前义务**：DOD-13「至少完成一次升级/恢复验证」——S8 演练同时覆盖升级与回退路径并记录证据。

**升级运行形态（落地手册；2026-10-14 ADR D14，U1）**：三相位 CLI——`upgrade pre-backup` / `upgrade gate` / `upgrade post` + 部署侧（容器编排/演练脚本）串接，不做一次性长命令、不做管理端点（B1/RS1 同因：闸门进程内语义——CLI 经运行实例端点诚实断言；产物传输不绑长请求）。流程步骤映射：

| 流程步骤 | 落地面 |
|---|---|
| 读发布说明兼容矩阵 | 部署侧人工/发布物料（不在代码面） |
| 开维护模式 | `upgrade pre-backup` 内置（HTTP 控制缝与备份 CLI 同款；幂等） |
| **升级前一致备份（强制）** | `upgrade pre-backup`（U2 维护不关闸）+ `upgrade gate`（U3 强制面） |
| 更新镜像 | 部署侧（换容器/镜像标签——CLI 不越权承担进程编排，RS1 同因） |
| 启动并自动迁移 | 镜像启动机制自身（启动即迁移，既有；`NOTEGIT_MAINTENANCE_ON_START=1` 维持维护连续——RS2 机制复用） |
| 冒烟检查 | `upgrade post`（healthz + 维护断言 + 迁移形态核对）+ 读面/写面冒烟（U4 步骤序） |
| 对账 | 对账域 CLI（reconcile）在维护内复跑 |
| 关闭维护模式 | **外部显式操作**（DELETE 维护端点）——RS1 步骤 10 同构 |

- **升级前备份的维护不关闸（U2；§4 步骤 7 与本节的分叉点）**：例行备份完成即关闸（§4 步骤 7）；升级前备份**不关闸**——升级全程处于维护模式（备份 → 换镜像 → 启动迁移 → 冒烟 → 对账 → 显式退出），备份后顺手关闸 = 换镜像窗口脱离维护，违背「升级全程维护、业务零写入」前提（回退零损失的根基）。完成审计行同 kind `backup.completed`，detail 增 `upgrade_pre_backup: true` 注记（§3「运维行随回退丢弃」时可辨）。排空超时中止**不设显式继续通道**（例行备份的 `--force-drain-timeout` 不进升级相位）：升级前备份是回退唯一依据，异常态下继续升级不可接受——与例行备份（管理员可裁定继续）不同层。
- **D-BR-08 强制面的机器可断言形态（U3）**：「升级前备份强制、未完成不得升级」的执行面 = `upgrade gate`：跳过（`--skip-pre-upgrade-backup`，解析面可表达、执行面**必拒**——为「跳过升级前备份被流程拒绝」提供显式断言位）、无证据（缺 `--data-item`）、证据不可信（离线验证全量复算失败）均退出非零并点名 D-BR-08/stage；放行 = 备份件可验证 **且** manifest schema ≤ 当前镜像（高于当前镜像的备份当前二进制读不懂，回退失据，同样不得作为升级依据）。gate 是纯核对面（不动数据、不动闸门）——「不得升级」的物理边界在换镜像动作本身（部署侧），gate 把该边界的判据做成可复跑命令。
- **冒烟步骤序（U4 裁决）**：可执行序 = **维护内冒烟读面（healthz/登录/关键读面，写仍 503 属预期）→ 恢复对账（维护内）→ 派生重建（如迁移新增派生表）→ 显式退出维护 → 冒烟写面（一次 push + 一次网页提交，同时充当「升级接受」判据）**——写冒烟在维护内必被拒（§3 写分类），对账在维护外必拒（fail-closed），「迁移后先写冒烟再退出维护」的箭头序不可按字面执行。
- **跨版本演练的旧版本构造口径（U5）**：无历史版本镜像时，「旧版本实例」= 当前镜像 + schema N-1 库（迁移回退手术仅演练构造用，非产品能力）。被证得：新二进制对旧 schema 库的启动自动迁移（前向、有序、重启可重入）、本节流程序与强制面、回退 = 备份恢复全链。不能证得：旧二进制自身的运行行为（不存在旧二进制）——升级前备份由当前二进制执行，回退版本核对断言锚定 **manifest 值**（回退后 schema 行集 == manifest.schema_version），不锚定「旧版 = N-1」。
- **回退丢弃口径实证（U6）**：备份点**后**写入的运行态（`backup.completed` 审计行、升级窗口登录会话、升级接受后的冒烟发布）随回退消失；备份点**前**的（`maintenance.enable` 行、种子期会话）随备份恢复保留。升级接受后的业务写随回退丢弃是**回退语义本身**（回退到备份点），与「零损失」不冲突：零损失锚定备份点，以「回退后业务态逐项 == 升级前态指纹」证得。

## 10. 待定项、任务关系与决策汇总

**待定项**：DB 引擎与快照/回灌命令（T1）；备份调度形态（定时编排：应用内定时 vs 外部调度，留部署规格——**触发形态已定稿：随发行包分发的 CLI 外部触发（2026-10-14 ADR D14，B1，见下注）**）；密钥件加密载体（企业选择）；备份频率/RPO/RTO 数值（Q9，S8 前与试用企业落实）；maintenance 错误码（T5）；备份件校验命令（T6 gates）。

**备份触发形态（选型；2026-10-14 ADR D14，B1）**：随发行包分发的 CLI（`node src/backup/cli.ts backup …`），不做管理端点。依据：闸门是**应用进程内**同步标志（§3 生效机制）——备份执行者是另一进程，唯一诚实的开闸路径是实例自己的维护端点（POST/DELETE /api/v1/admin/maintenance）；脚本经 HTTP 控制面驱动开/关闸并逐一复核（enable 后 GET 复核 enabled=true，fail-closed）——一个「在备份工具自己进程里翻转的闸门」是假闸门（实例照常收写）。快照工作是文件系统/DB 层作业（VACUUM INTO、目录复制、抽样 fsck），产物落运维指定的输出根（可跨介质——`--keys-out`），天然不宜绑定在长 HTTP 请求上；端点形态会让「触发备份」与「排空等待（默认至多 300s）」共占一个请求生命周期，超时语义与 §4 步骤 2 的「中止并保持维护」难以在 HTTP 层诚实呈现。被否决备选：管理端点 POST /api/v1/admin/backup（HTTP 超时耦合大目录复制、产物默认落服务自身卷与分置精神相悖、闸门归因反而更绕）。该 CLI 已是外部触发的最小完备形态，调度形态（定时编排）留部署规格。

**任务关系**：S2 实现维护模式闸门与凭据域（identity 契约）；S3 的 receive 预记录与排空对接本契约 §4 步骤 2；S8 按本契约演练并记录证据（Q8/DOD-12）；T2 错误协议承载维护模式拒绝响应；T5 固化 API 侧语义；T6 固化校验命令。
